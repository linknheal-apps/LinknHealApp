# Problem M2: entries_select_shared subquery predicate removal

## Problem
Patch `.mutation/M2.patch` removes `and s.shared_with_user_id = (select auth.uid())` from `entries_select_shared`:
```sql
 create policy entries_select_shared on public.entries
   for select to authenticated
   using (
     private.is_actively_linked_to(entries.owner_id)
     and exists (
       select 1 from public.shares s
       where s.entry_id = entries.id
-        and s.shared_with_user_id = (select auth.uid())
     )
   );
```
Status: `EQUIVALENT-DOCUMENTED` (for M2); `KILLED-BY-NEW-TEST` (for M2c).

---

## Evidence So Far
- **PostgreSQL 17 Row Security Policies Documentation (`ddl-rowsecurity.html`):**
  - URL: https://www.postgresql.org/docs/17/ddl-rowsecurity.html
  - Excerpt [UNVERIFIED]: *"If it is necessary to consult other rows or other tables to make a policy decision, that can be accomplished using sub-SELECTs, or functions that contain SELECTs, in the policy expressions."*
- **Mechanism:**
  - `public.shares` is protected by `shares_select_parties`:
    `using (owner_id = (select auth.uid()) or shared_with_user_id = (select auth.uid()))`
  - Subqueries in RLS policies run under the security context of the current authenticated role.
  - Non-owners querying `public.shares` via the subquery can only see rows where `shared_with_user_id = auth.uid()`.
  - Composite FK `shares(entry_id, owner_id) REFERENCES entries(id, owner_id)` ensures share rows can only exist for entries matching the owner.
  - Mutation `M2b` (`.mutation/M2b.patch`), which combines M2 with opening `shares_select_parties` to `using (true)`, is KILLED by tests 12 and 13 in `03_sharing.test.sql` (commit 739ba77).
  - Mutation `M2c` (`.mutation/M2c.patch`), which opens `shares_select_parties` to `using (true)` while keeping the explicit predicate in `entries_select_shared`, is KILLED by tests 4, 5, and 6 in `07_shares_visibility.test.sql` (commit 0f76ae1).

### Explicit Statement of Dependencies and Limitations (What is NOT Proven)
- **Equivalence Assumption:** M2 is an equivalent mutant **only while `shares_select_parties` is unchanged**. The equivalence holds because the subquery on `public.shares` inherits the row-level security of `shares_select_parties`. `07_shares_visibility.test.sql` pins and guards this dependency by asserting that third parties and strangers cannot view unshared share rows.
- **What is NOT Proven:** M2 equivalence is argued from the policy definitions and the composite foreign key, and confirmed empirically only by the survival of M2 and the M2c contrast. It is not proven by exhaustive mathematical or formal methods.

## Analysis of Test Coverage Gap on public.shares under Mutation M2c

### Why `02_entries_isolation.test.sql` Test 22 Did Not Fail under M2c
In `supabase/tests/database/02_entries_isolation.test.sql`, test 22 asserts:
```sql
92: reset role;
93: set local role authenticated;
94: set local request.jwt.claims = '{"role":"authenticated"}';
95: select is((select (select count(*) from public.users) + (select count(*) from public.partner_links)
96:                 + (select count(*) from public.therapist_client_links) + (select count(*) from public.entries)
97:                 + (select count(*) from public.shares))::int,
98:           0, 'T11 authenticated role without a user identity gets zero rows from every table');
```
Test 22 does query `public.shares` (`(select count(*) from public.shares)`), but it returns `0` even under mutation M2c because **the fixture in `02_entries_isolation.test.sql` does not contain any rows in `public.shares` at that point (or at any point in the file)**.
- Lines 21-34 seed `auth.users`, `public.users`, `public.partner_links`, `public.therapist_client_links`, and `public.entries`. No rows are inserted into `public.shares`.
- Throughout `02_entries_isolation.test.sql`, `share_entry()` is never called.
- Therefore, `select count(*) from public.shares` evaluates to `0` simply because the table is empty, creating a vacuous pass under M2c (`using (true)`).

### Why `03_sharing.test.sql` Did Not Fail under M2c
In `supabase/tests/database/03_sharing.test.sql`, share rows are created via `share_entry()`, but:
- Queries targeting `public.shares` directly only asserted:
  - Line 40: as owner A: `select count(*) from public.shares where entry_id = ... and shared_with_user_id = B` is 1 (passes under M2c).
  - Lines 68-76: recipient B cannot delete or update `public.shares` (permission denied / 0 rows; tests table grants/delete policy, not select policy).
  - Lines 97-101: owner A revokes share via delete (passes).
  - Lines 109-110: unlinked user direct insert into `public.shares` denied (grants check).
- Crucially, `03_sharing.test.sql` lacked assertions verifying that an unlinked stranger or a non-recipient third-party cannot read `public.shares`. All entry reads were guarded by the outer policy, leaving direct read visibility on `public.shares` untested.
