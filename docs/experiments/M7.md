# Problem M7: entries_update_own with check (true)

## Problem
Patch `.mutation/M7.patch` changes `entries_update_own` from:
```sql
create policy entries_update_own on public.entries
  for update to authenticated
  using (owner_id = (select auth.uid()))
  with check (owner_id = (select auth.uid()));
```
to:
```sql
create policy entries_update_own on public.entries
  for update to authenticated
  using (owner_id = (select auth.uid()))
  with check (true);
```
Status: `EQUIVALENT-DOCUMENTED`.

---

## Evidence So Far
- **PostgreSQL 17 Row Security Policies Documentation (`ddl-rowsecurity.html`):**
  - URL: https://www.postgresql.org/docs/17/ddl-rowsecurity.html
  - Excerpt [UNVERIFIED]: *"Typically an UPDATE command also needs to read data from columns in the relation being updated (e.g., in a WHERE clause or a RETURNING clause, or in an expression on the right hand side of the SET clause). In this case, SELECT rights are also required on the relation being updated, and the appropriate SELECT or ALL policies will be applied in addition to the UPDATE policies."*
- **PostgreSQL Source Code (`src/backend/rewrite/rowsecurity.c`):**
  - URL: https://github.com/postgres/postgres/blob/master/src/backend/rewrite/rowsecurity.c
  - Excerpt [UNVERIFIED]: *"Get and add ALL/SELECT policies, if SELECT rights are required for this relation (eg: when RETURNING is used). These are added as WCO policies rather than security quals to ensure that an error is raised if a policy is violated; otherwise, we might end up silently dropping rows to be added."*
- **Mechanism:**
  - Layered defense:
    1. **Layer 1:** `entries_update_own WITH CHECK (owner_id = (select auth.uid()))`.
    2. **Layer 2:** `entries_select_own USING (owner_id = (select auth.uid()))`, which PostgreSQL applies as a WithCheckOption (`WCO_RLS_UPDATE_CHECK`) on the `NEW` row of an `UPDATE` when `SELECT` rights are required on the target table (such as targeting via `WHERE id = ...`).
  - Either layer independently prevents an owner from transferring ownership to another user (`owner_id := B`), throwing SQLSTATE `42501` (`new row violates row-level security policy for table "entries"`).
- **Paired Mutation Evidence:**
  - Mutation `M7` opens Layer 1 (`WITH CHECK (true)`), but Layer 2 blocks reassignment. M7 SURVIVES.
  - Mutation `M7b` opens both Layer 1 (`WITH CHECK (true)`) and Layer 2 (`entries_select_own USING (true)`). M7b is KILLED (CI run on commit 0f76ae1, Tests=93, Result: FAIL). Reassignment-specific failures: `06` tests 2-3 and `05` tests 1-2. The remaining failures (`06` test 4 and tests in `02`, `03`, `04`) come from the read policy opened by `entries_select_own USING (true)`, not from reassignment.
  - Mutation `M7c` opens Layer 2 (`entries_select_own USING (true)`) while leaving Layer 1 intact. (See attempt log below).
